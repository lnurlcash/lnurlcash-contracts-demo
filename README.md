# LNURLcash Contracts Lab

A deliberately small real-sats demonstration of two different claims:

1. A payment can be made into an LNURLcash output whose secret was generated by the recipient. The sender funds only its SHA-256 hash and can never spend the resulting note.
2. A cancellation bond can be enforced today only by giving some party enough control to refund or redirect it. This demo calls that party the referee and calls the arrangement custodial.

The app is static. It has no application backend, analytics, service worker or remote JavaScript. The public build talks only to the allowlisted experimental ForgeSworn mint, pins its withdraw endpoint and signing key, caps every real transfer at 500 sats and asks for exact-value disposable notes.

`lnurlcashlock1` is an experimental, signed receiver-lock request used by this lab. It is not part of the current LUD-25 draft and must not be presented as an interoperable standard. The point of the site is to put a real implementation in front of the LNURLcash developers so the request and conditional-output discussion has working evidence behind it.

## Run it

```bash
npm install
npm run check
npm run dev
```

Open the printed local URL. For a real transfer, cut an exact-value note in Notecase or another LUD-25 wallet, then paste that disposable note into the relevant payer panel.

## Internet hand-off

The recipient or referee can copy an internet hand-off link and send it through Signal, email, Nostr or another existing channel. The signed request is carried in the URL fragment, so a static host does not receive it in the HTTP request. It contains the amount, mint, contract metadata and receiver output hash, but not the receiver's spend secret. Do not put a bearer note in a link.

This makes recipient-locked payment and remote bond funding multi-device flows: the payer opens the link, checks the signed details and funds from its own browser; the receiver/referee independently probes the mint. Full remote bond resolution is deliberately not claimed yet. The current inspector simulates rider and driver outcome signatures locally. The next acceptance gate is a participant-key handshake and portable signed outcome messages, tested across three clean browser profiles.

The exact remote state machine and hosting trust boundary are in [`docs/REMOTE-COORDINATION.md`](docs/REMOTE-COORDINATION.md). The current hostile-path verdict and remaining gates are in [`ADVERSARIAL-REVIEW.md`](ADVERSARIAL-REVIEW.md).

## What the bond lab does

- The referee generates and persists two independent receiver secrets before publishing the rider and driver bond requests.
- Each party rotates an exact-value note directly into its bond hash. The payer never knows the referee's new secret.
- Completion redirects each bond to a fresh output for its original owner.
- A rider-signed cancellation redirects both notes to the driver. A driver-signed cancellation does the reverse.
- A dispute moves nothing. Silence and GPS evidence are not self-authenticating outcome oracles.
- If setup expires with only one verified bond, the referee refunds that funded side.

The single-browser outcome UI holds all three demo roles to make the state machine inspectable on one screen. A real implementation must keep the two parties' and referee's secrets on separate devices. DonkeyRide is the worked example: its NIP-17/NIP-59 conversation could carry the signed requests and outcomes privately, but transport is outside this lab's present proof.

## The missing primitive

Removing the referee requires mint-enforced spending conditions: signatures, multiple branches and a timeout/refund path. Plain LUD-25 has one bearer secret and none of those branches. See [docs/CONDITIONAL-BONDS.md](docs/CONDITIONAL-BONDS.md), [THREAT-MODEL.md](THREAT-MODEL.md) and [ADVERSARIAL-REVIEW.md](ADVERSARIAL-REVIEW.md).

## Hosting

The public lab is live at [`labs.moneyer.dev`](https://labs.moneyer.dev). It says what this is without implying that conditional bonds are already a stable Moneyer feature. The exact release, asset hashes and rollback location are recorded in [`DEPLOY.md`](DEPLOY.md).

The static host must send security headers rather than relying on HTML for directives browsers do not accept there. At minimum:

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' https://mint.forgesworn.dev; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```
